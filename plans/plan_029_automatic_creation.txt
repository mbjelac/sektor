New sektors can be automatically created using an algorithm.
Each sektor has a level, and a palette of buildings which may be placed in it.

Sektor complexity is (for now) determined by:
- allowed buildings
    - fewer buildings which help = more complex
    - more buildings which do not help = more complex
- requirements & restrictions
    - more strict = more complex
    - more of them = more complex
- location properties
    - lower numbers = more complex

Requirements and restrictions are grouped together so that for a given requirement, restrictions are placed on input resources of the building which produces the required output.
This forces the player to not just put a building which produces the required output, but also buildings which produce the input for that building, etc.
Placing restrictions like this can be done in layers, forcing player to move backwards in the production chain, placing more buildings as more inputs are needed.
Most buildings have more inputs than outputs. Restrictions don't need to be placed on all building's inputs, just one.
A multi-layer restriction plan can then have one restriction per layer.
Example:
    - for these production chains (lowercase letters are resources and Bx are buildings):
        a,b>B1>c
        c,d,e>B2>f
    - a requirement can be put for f
    - 1st restriction layer can be put only on c (not d & e)
    - 2nd restriction layer can be put on a (not b)

If a building produces a resource needed for a requirement, directly or indirectly,
and that resource is not specified with an amount but referenced by a location property,
a sektor complexity can be modified by controlling the location property matrix values of that property.
Example:
    - a requirement is FoodRaw
    - Agriplot produces FoodRaw but needs WaterPottable
    - WaterWells produces WaterPottable but needs groundwater (location property)
    - if a sektor is to be more complex, do not create groundwater matrix with high values

THE BACKWARD WALK

Allowed buildings are the crucial knob, because choosing them and choosing the restrictions in the
same backward walk makes the sektor solvable by construction. The walk is:
    - start at a required resource
    - pick a building which produces it and put that building in the palette
    - pick one of that building's inputs and restrict it
    - the restricted input becomes the current resource, and the walk repeats

When the walk ends, every restricted resource has a producer in the palette, and the chain ends at
something the player can either import freely or pull out of the ground. The walk has therefore
built a solution the player can place. Nothing has to be solved or simulated to know the sektor can
be finished.

This only holds if the palette and the restrictions are chosen together, in one pass. Choosing a
palette first and restrictions afterwards brings back the failure: leaving WindLoop and SunCatcher
out of the palette while restricting EnergyElectric gives the player no local producer and no import
allowance, and the sektor is dead.

RULE: Do not impose a restriction if it makes the sektor unsolvable! Same goes for location properties - do not put all 0s if this resource is needed to solve the sektor.
The walk satisfies this rule by construction. It is still a rule, for anything added to a sektor outside the walk.

PALETTE BEYOND THE WALK

A palette holding only the walk's buildings is constrained but easy - every building is needed and
there is nothing to work out. What makes a palette hard is having to find which buildings matter. So
two more kinds of building go in, in opposite directions:
    - alternatives - other producers of a resource already on the walk
        - more of them = more ways to succeed = easier
        - so their number falls as level rises
    - distractors - buildings which produce nothing on any walk
        - more of them = more to sift through = harder
        - so their number rises as level rises
        - they can never make a sektor unsolvable, because the walk's buildings are already in

COMPLEXITY BY LEVEL

Every knob is an absolute function of the level, not a table, because there is no highest level.
Absolute means a sektor of a given level stays the same amount of work as buildings.md grows, so
sektors made now stay comparable to sektors made later. New buildings instead raise the ceiling:
they lengthen the longest production chain, which lets levels above today's clamp become real.

    requirementCount    = 1 + floor(level / 2)
    restrictionLayers   = min(1 + level, longest backward chain from the required resource)
    restrictionValue    = max(0, 4 - level)
    alternativeCount    = max(0, 3 - floor(level / 2))
    distractorCount     = level
    propertyMinimum     = max(1, MODIFIER_MAX - level)

What these work out to today, as illustration only:
    - level 1: 1 requirement, 2 restriction layers, imports allowed up to 3, 3 alternatives per
      restricted resource, 1 distractor, needed properties in 5..6
    - level 2: 2 requirements, 3 layers, imports up to 2, 2 alternatives, 2 distractors, 4..6
    - level 3: 2 requirements, 4 layers, imports up to 1, 2 alternatives, 3 distractors, 3..6
    - level 4: 3 requirements, 5 layers, no imports of restricted resources, 1 alternative,
      4 distractors, 2..6

NOTE: a sektor's storage could be split in two, its initial definition and its current state. That
is a performance optimization only, and is not done here.

CONCLUSIONS

Playing the generated sektors showed them to be hard, and meeting a requirement to be barely worth
the imports it took. Working out why turned up the following, in rough order of how much each one
matters. Most of it is about the economy rather than about the making of sektors, but it is written
down here because it is what the making of sektors ran into.

1. Importing a negative-scoring resource pays.
    applyNegativeScoring flips the sign of a score, and it is applied to imports as well as exports.
    So a resource marked negative — Work, WaterSewage, WasteBio — earns 2 a unit when brought in.
    This is very probably not what "negative" was meant to say, and it is the largest single force
    in the economy:
        - a Polytechnic fed on imported Work, its energy from a wind loop, is worth about +20 a
          building with no requirement met at all: around +1860 on a full map
        - imported sewage makes WaterTechnical cost less than nothing, which quietly subsidises
          every chain which touches water
    Everything else in the economy is worth tuning only after this is decided. Exporting waste being
    bad does not obviously mean being paid to take waste in.

2. Every unit of every resource is worth the same.
    Two points, whatever it is. So a building can only pay by making more units than it eats, and a
    recipe which says "much of something cheap becomes a little of something precious" cannot pay,
    however its numbers are set. Refining is exactly that shape. This is structural rather than a
    matter of the numbers in buildings.md, and it gets worse with every resource added, not better.
    Worth per resource, kept in resources.md, would fix it without breaking the rule that a unit
    costs on the way in exactly what it earns on the way out. It is also the same mechanism that
    requirements driven by global scarcity would need: scarce, so valuable, so worth requiring.

3. A requirement cannot be met by importing.
    Imports and exports are both worked out from what buildings eat and make, so there is no buying
    and re-selling. To export something the sektor has to make it. This means a requirement has no
    floor: a sektor can be finished exactly as asked and leave the player worse off than an empty
    one. Requirements chosen by scarcity will need a check for this, or the algorithm will keep
    asking for the one thing nobody can afford to make — and nobody making it keeps it scarce.

4. What was changed, and what it measured at.
    Location property maximum raised from 6 to 12, and every fixed output in buildings.md doubled.
    Extraction is fed by location properties and processing by fixed amounts, so the two levers are
    disjoint and both were needed. Afterwards, measured over 25 generated sektors a level:
        level  1: finished 20/25, median score  84, median  3 buildings
        level  3: finished 14/25, median score 238, median 15 buildings
        level  6: finished 10/25, median score 364, median 29 buildings
        level 10: finished  7/25, median score 436, median 41 buildings
    No sektor at any level left the player worse off. Sektors are worth playing now; how many of
    the unfinished ones are unfinishable rather than merely unplayed is not yet known (plan 30).

5. A local resource needs a producer in the palette.
    A restriction only caps what may be imported, and the walk always supplies a local route for
    whatever it restricts. A local resource is stricter: it cannot be imported at all, so a building
    which eats one is useless unless the palette also holds something which makes it. Fixed.

6. Left open.
    Whether Work should be local rather than negative. Making it local kills the Polytechnic loop
    and makes shortages visible through starvation instead of being papered over by imports, which
    both read as improvements — but it does not by itself force a player to house their workers,
    since WorkTechnical and WorkMaintenance stay importable one step downstream. Decide the negative
    import rule first; this depends on it.
